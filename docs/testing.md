# Testing

The automated suites run in CI; the cases that cannot be automated are run by hand, and every manual run is recorded with its date, Umbraco version and commit.

## Automated

| Suite | Command | Needs |
|---|---|---|
| Unit tests (NUnit) | `dotnet test Umbraco.Community.PropertyVisibility.slnx -c Release` (CI: `bash build/ci/test.sh`) | .NET 10 SDK |
| Acceptance (Playwright) | `npm ci`, `npx playwright install chromium`, `npm run test:acceptance` in `tests/Umbraco.Community.PropertyVisibility.AcceptanceTests` (CI: `bash build/ci/start-test-site.sh`, `bash build/ci/acceptance.sh`, `bash build/ci/stop-test-site.sh`) | the test site running on https://localhost:44300; `PV_BASE_URL` selects another site, and the `build/ci` scripts take `PV_PORT` |
| Schema drift | `dotnet run --project tools/Umbraco.Community.PropertyVisibility.SchemaGenerator -c Release --no-build -- --out src/Umbraco.Community.PropertyVisibility --check` (after a Release build; CI: `bash build/ci/schema-check.sh`) | .NET 10 SDK |
| Package inspection | `bash tools/inspect-nupkg.sh <folder with nupkg> <version>` (CI: `bash build/ci/pack.sh`, and `bash build/ci/test-inspect-nupkg.sh` as its leak test) | bash, unzip |

`ci.yml` runs all of them on every pull request and push to `main`: build, unit tests, schema drift, pack and inspection, then the whole Playwright suite against the test site on `ubuntu-24.04` (SQLite, clean database). `compat.yml` builds against the latest Umbraco 17.x every Monday (every `Umbraco.Cms` package at exactly that version), type-checks the client against that version's `@umbraco-cms/backoffice` typings, and runs the unit tests, the schema check and the whole Playwright suite; it opens an issue when that fails or when a scheduled run is cancelled by its timeout. GitHub disables the schedule after 60 days without repository activity (see [CONTRIBUTING.md](../CONTRIBUTING.md#run-ci-locally)). The scripts are described in [CONTRIBUTING.md](../CONTRIBUTING.md#run-ci-locally).

For a clean acceptance run, stop the test site, delete `src/Umbraco.Community.PropertyVisibility.TestSite/umbraco/Data`, and start it again: the boot installs unattended on SQLite and imports the uSync set in `uSync/v17`. The acceptance suite creates an "Acceptance landing ...", an "Acceptance blocks ..." and an "Acceptance validation ..." (saved, not published) document under "Corporate site" on every run, and saves "Corporate landing" (its values stay the same). Spec `22` creates an "Acceptance root ..." document at the content root and deletes it again through the Management API. The seed has two languages (en-US, the default, and da-DK) and one culture-variant document, "Corporate variant page" (document type `variantPage`, both cultures published; uSync's first-boot import leaves its en-US variant as published with pending changes); every other document is invariant. Spec `20` makes `landingPage.metaTitle` and `promoBannerSettings.anchorId` mandatory through the Management API for the length of the test and sets them back in `finally` (the test site does not export to uSync on save, so the seed files never change).

The acceptance specs run serially in one worker, in file name order:

| Spec | Covers |
|---|---|

| `10-config-file-reload` | Writes `PropertyVisibility.config.json` into the running site's content root: its rules replace the appsettings rules and an emptied group disappears; deleting the file brings the appsettings rules back, without a restart. |
| `11-appsettings-reload` | Sets `PropertyVisibility:Enabled` to `false` in the running site's `appsettings.json`, then restores the file byte for byte, without a restart. |
| `12-health-check` | The health check through the Management API: Success on the sample; `PV201`, `PV101`, `PV203` and `PV301` for a deliberately wrong rules file; `PV001` with the last valid rules kept for invalid JSON; Success again afterwards. |
| `13-blocks-modal` | A Block List block edited in a modal (`landingPage.mainBlocks`): `promoBanner.overlayColour` hidden on Corporate landing, shown on Campaign landing. |
| `14-blocks-inline` | The same for an inline-edited Block List block (`landingPage.inlineBlocks`), expanded in place. |
| `15-blocks-grid` | The same for a Block Grid block edited in a modal (`landingPage.gridBlocks`). |
| `16-blocks-settings-and-containers` | The Settings half (`promoBannerSettings.anchorId` and its emptied group hidden on Corporate, shown on Campaign, next to the never-hidden `cssClass` in its "Layout" group), and a tab removed inside a block (`callToAction` has no `settingsTab` on Campaign, in `mainBlocks` and `gridBlocks`). |
| `17-blocks-nested` | A `promoBanner` inside a `contentSection` block (two modal levels): both halves follow the site. |
| `18-blocks-unsaved-document` | A new landing page under Corporate site: a `promoBanner` added through the block catalogue to `mainBlocks` (modal) and to `inlineBlocks` (inline) hides `overlayColour` and `anchorId` before the first save (requested with the parent), and again after it (requested without): the inline block applies again by itself, the modal block when it is reopened. On 17.6.2 the first save re-creates the inline block (the create route becomes the edit route); the spec records which happened as an annotation. |
| `19-blocks-requests-and-reopen` | One request per document and element type while the inline, modal, grid and nested blocks apply, none when a modal is reopened; hidden block values unchanged after Update and Save; the applied event's block targets. |
| `20-hidden-mandatory-validation` | A new landing page under Corporate site whose hidden `metaTitle` (in the removed `seoTab`) and hidden `anchorId` (in a modal and an inline `promoBanner`, whose Settings group is removed) are mandatory and empty: Save and publish shows Umbraco's "could not be published" notification, the document stays a draft, the fields stay hidden, and no console error or uncaught error appears. The server validation answers 400 on purpose; the spec declares that request (fixture `expectedRequestFailures`). |
| `21-blocks-outside-document` | The media item "Promo media" (inline Block List with a `promoBanner`), opened from the Corporate landing `promoBanner`'s image (media picker, "Open in Media Library") and from the Media section: `overlayColour` shown, no block pass, no hidden-fields request. |
| `22-create-at-root` | Two documents created at the content root with the Content tree's Create action. A `site` document: requested without a parent, root resolution `None`, the `IsDefault` site (`everythingElse`); after the first save it is its own root (`Document`) and still matches the default site. Before and after the save the top-level `siteSettings` rule, keyed by a composition of `site`, removes the composition's copy of the Legacy tab, its General group and both properties, with the same keys the API returns for `siteSettings` itself; the site type's own Legacy tab stays with `siteNotes`. A landing page created under the new root gets the default site's rule (`bannerImage` hidden, `seoTab` and `settingsTab/advanced` shown) and a `promoBanner` added to it keeps `overlayColour` and `anchorId`. A `landingPage` at the root (the test allows `landingPage` at the root through the Management API and sets it back in `finally`): before the first save the document and a `promoBanner` added in a modal (both halves) are requested without a parent, root resolution `None`, the default site; `bannerImage` is hidden, `overlayColour` and `anchorId` are shown. After the save the document and the reopened block resolve to `Document`, and `bannerImage` stays hidden. Both documents are deleted at the end. |
| `23-split-view` | "Corporate variant page" in split view, en-US and da-DK side by side (the variant selector's "Open in split view"): in both panes the `seoTab` tab and the variant `variantTagline` are hidden by the Corporate rule, the variant `variantTitle` (with each culture's value), the invariant `sharedNote` and the invariant block list are shown; the `promoBanner` opened from either pane hides `overlayColour` and `anchorId`; closing the da-DK pane leaves en-US hidden the same way. |
| `24-composition-rules` | The seeded "Corporate site" (matched by key) and "Campaign site" (matched by name) documents. The top-level rule keyed by `siteSettings` returns only the composition's keys (its Legacy tab copy, its General group and both properties, the same keys as for `siteSettings` itself), never the site type's own tab or `siteNotes`; in the editor the Legacy tab stays with `siteNotes` visible, and the General group, `siteTitle` and `footerText` are gone. |
| `99-measure-inline-block-error` | Opt-in measurement, skipped unless `PV_MEASURE=1`: opens both landing pages 45 times each (`PV_MEASURE_RUNS`) and counts the known upstream inline-block error. `PV_MEASURE_MODE=fresh` (default) only loads the page, which does not trigger the error; `PV_MEASURE_MODE=tabclick` also clicks the already selected Content tab as soon as it shows, the trigger that reproduces it. Not a pass/fail check. |
| `08-console-errors` | Runs last (the `console-errors` teardown project in `playwright.config.ts`): no console errors in any spec of the run, plus a tour of every page the package touches, block modals included. |

The block specs find blocks by the attributes Umbraco 17.6.2 renders, not by text: `umb-property[data-mark="property:<alias>"]` for a property (a property hidden in a block is not rendered at all), `umb-block-list-entry` and `umb-block-grid-entry` with `data-content-element-type-alias`, the block actions `uui-button[data-mark="block-action:Umb.BlockAction.EditContent"]` and `...EditSettings`, the view links `uui-tab[data-mark="workspace:view-link:Umb.WorkspaceView.Block.Settings"]` and the workspace actions `...Umb.WorkspaceAction.Block.SubmitCreate` / `SubmitUpdate` (`support/blocks.ts`). They wait for the applied event of the block half (`waitForBlockApplied`: document key, element type key, `block-content` or `block-settings`, and a `since` time taken before the action). The seeded landing pages open with `openDocumentWithInlineBlocks`, which also waits for the passes of the inline blocks (same element types, same counts), so a `since` wait afterwards belongs to the modal, grid or nested block. A hidden property is only checked next to a visible one of the same view (`heading`, `cssClass`), so "hidden" never means "not rendered yet".

To measure the upstream error: `PV_MEASURE=1 PV_MEASURE_MODE=tabclick npx playwright test tests/99-measure-inline-block-error.spec.ts --no-deps` (PowerShell: set `$env:PV_MEASURE` and `$env:PV_MEASURE_MODE` first). The counts are printed, shown as annotations on the report and written to `test-results/inline-block-error-measurement.json`.

Specs `10` to `12` change the running site's configuration and restore it in `finally` blocks; they expect the test site to be the one in this repository (override its folder with `PV_SITE_CONTENT_ROOT`), and they refuse to start when a `PropertyVisibility.config.json` already exists there. The console-errors spec counts every console error and uncaught page error except the known Umbraco errors listed in `support/fixtures.ts` (`KNOWN_UPSTREAM_ERRORS`), which are logged as `upstream` lines and shown as annotations on the report. The only entry: on Umbraco 17.6.2 and 17.7.0 (not fixed in 17.7.0) an inline-edited Block List item that is re-rendered while it initializes throws "Context request was cancelled, host was disconnected (UmbBlockEntriesContext ... UMB-INLINE-LIST-BLOCK)" as an uncaught rejection (`UmbBlockWorkspaceContext.load()` is called without a catch). The trigger is a re-render of the tab view while the inline blocks load: a full page load followed by a click on the already selected Content tab. Reproduced on a stock 17.6.2 site with the package removed (no package assembly, static assets or manifest; uSync only imported the test content): 0 of 90 fresh page loads, 4 of 90 loads followed by that click, 18 of 40 with 4x CPU throttling (run 2026-09-25, recorded under [Manual acceptance runs](#manual-acceptance-runs)). Any spec that opens a landing page with inline blocks can hit it; runs so far saw it in specs `05`, `10` and `11` (`10` and `11` open a landing page after a configuration change and then call `openContentTab`). A test that fails a request on purpose declares it (fixture `expectedRequestFailures`: URL, status and reason); only the browser's "Failed to load resource" message for that request is logged as an `expected` line instead of an error. The global setup copies `appsettings.json` into the gitignored `.run-state/` folder and fails fast unless `PropertyVisibility:Enabled` is `true` and no rules file exists; the global teardown restores the copy and deletes a rules file the suite wrote when an interrupted test did not, and the next run's setup does the same after a hard kill. Waits use the package's applied event, a network response or a rendered element, each with a timeout, never a fixed delay: `settle()` waits for the hidden-fields requests in flight and their applies, then two animation frames, and a step that expects no request waits for what the page renders instead (Save and publish waits for Umbraco's "Document published" notification). Configuration reloads are polled until the API or the health check reports the new state. Only the opt-in measurement (`99`) waits a fixed 250 ms after each page load, to count a late rejection. To run one spec, pass `--no-deps` (for example `npx playwright test tests/05-backoffice-visibility.spec.ts --no-deps`); without it the console-errors teardown runs too and fails, because the other specs did not run.

## Manual acceptance runs

Blocks inside blocks (`17-blocks-nested`), creating a document at the content root (`22-create-at-root`) and split view (`23-split-view`) are covered by the acceptance suite. These cases are not automated, because each needs a change to the test site's document, member or data types that the other specs must not see; they are run by hand (or scripted outside the suite) against the test site with the sample rules, on a database that is thrown away afterwards:

| Case | Steps | Expected |
|---|---|---|
| Blocks in the rich text editor | Add a Tiptap rich text property allowing `promoBanner` (with `promoBannerSettings`) to `landingPage`, insert the block on Corporate landing and on Campaign landing. | Corporate: `overlayColour` and `anchorId` hidden in the block modal. Campaign: both shown. |
| Single Block | Add a Single Block property allowing `promoBanner` to `landingPage`, in a modal and with inline editing. | Same as the rich text editor case. |
| Block clipboard paste | On Corporate landing copy the Main blocks `promoBanner` (block action Copy to clipboard), paste it into Main blocks of Campaign landing and open it; then the other way round. | The pasted block follows the site of the document it is pasted into; the copied values (including hidden ones) are kept. |
| Blocks in a member opened from a document | Add a Block List property allowing `promoBanner` to the Member type and a Member Picker to `landingPage`, create a member with a `promoBanner`, pick it on Corporate landing and open it from the picker. | `overlayColour` shown in the member's block (no site; the site boundary stops the request at the member workspace). |
| Blocks in a document blueprint | Create a document blueprint from Corporate landing and open its `mainBlocks` `promoBanner`. | `overlayColour` shown: blueprints have no site. |
| Block Grid inline editing | Turn on `inlineEditing` for `promoBanner` in the Blocks (grid) data type, hide `heading` (its first property) as well as `overlayColour` for Corporate site, open Corporate landing. | Documented limitation: `heading` is shown inline in the grid; in the block's modal `heading` and `overlayColour` are hidden. |

## Publication checklist: accepted exceptions

The test site carries two credentials on purpose. Both are dummies for a throwaway local SQLite database, live in `src/Umbraco.Community.PropertyVisibility.TestSite/appsettings.Development.json` (loaded only in the Development environment, which both launch profiles set) and are accepted exceptions for the secret scan before publication:

| Value | Why it is there |
|---|---|
| Unattended install login `admin@example.com` / `PropertyVisibilityDev1!` | Lets the test site install itself unattended and lets the acceptance suite log in. |
| `Umbraco:CMS:Imaging:HMACSecretKey` (base64 of the text "PropertyVisibility test site dummy HMAC key - not a secret") | Without a key, Umbraco generates a random one on the first unattended install and writes it into the tracked `appsettings.json`. The fixed dummy keeps that file unchanged. It only signs image URLs of the local test site. |

No other secret may appear in the repository.
